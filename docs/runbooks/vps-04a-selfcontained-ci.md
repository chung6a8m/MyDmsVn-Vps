## How automatic SQL CI works

The workflow runs on Ubuntu 24.04 for `pull_request` open/reopen/synchronize, `main` push and optional manual dispatch. No repository or Environment secrets are read.

1. Checks out the PR under read-only `contents:read`, no persisted credentials, and uses the nested .NET **10.0.404** SDK in `src/MyDmsVn.Server.AspNetCoreHost`. Legacy root `global.json` and Windows `net48` graph remain unchanged.
2. Generates unique strong per-job SA/runtime/oracle/writer/denied passwords and a JWT signing key. Values are immediately masked; kept only in the job environment, never committed, uploaded or printed. SQL port **1433 binds only to 127.0.0.1**. The SQL container has no persistent database volume and is removed with `docker rm -f -v` even if tests fail.
3. Runs Microsoft SQL Server **2022 Developer** container with forced TLS 1.2. Creates two ephemeral localhost-SAN certificates: one for SQL Server and one for Kestrel, locally trusted only within the disposable GitHub runner. The SQL Server account must read its private key (mode 0400, UID 10001) from an accessible container directory; the job explicitly checks this. No `-k`, `Encrypt=False`, or `TrustServerCertificate=True` is accepted.
4. Compiles **one CI-only .NET10 tool** `tests/MyDmsVn.Vps04a.SqlBootstrap` from the **original DbUp `DatabaseMigrationRunner`, migration lock/maintenance validator and unchanged SQL scripts 001–013**. It runs only on `GITHUB_ACTIONS=true` with explicit `VPS04A_CI_EPHEMERAL_SQL=approved-container-only`, exact loopback SQL SA connection and a fresh fixed-name database `MyDmsVnVps_Ci`. It refuses an existing database, wrong SQL endpoint or TLS trust bypass.
5. Verifies **13/13 original migrations, exact schema13 compatibility fingerprint**, seeds fresh active users and Customer/Warehouse/Employee/Product, provisions **restricted Web+Desktop runtime** using the reviewed `deployment/sql/Provision-MyDmsVnWebPrincipals.sql` and `Provision-MyDmsVnDesktopApiGrants.sql`, and independently grants Oracle **only SELECT** on exactly nine CI-owned tables: WebAuthSessions, WebOperationJournal, SalesReceipts, SalesReceiptLines, GoodsReceipts, GoodsReceiptLines, StockLedger, StockValuationEntries and StockBalances. The separately protected staging Oracle retains its own approved privilege policy.
6. Re-runs the **production** runtime-principal and superuser binding validators and asserts Oracle has neither broad privilege nor write rights. Connection strings for **only the disposable local SQL instance** and generated business seed IDs flow via the protected job-local `GITHUB_ENV` file. `VPS04A_RUNTIME_SQL` and `VPS04A_ORACLE_SQL` are **not needed** in CI; keep these names exclusively for protected staging.
7. Builds the production .NET10 host and opt-in tests with `-p:Vps04ALive=true`, launches real Kestrel HTTPS with TLS verification, and executes **6/6 normal SQL-backed facts**: the original 4 auth/idempotency/authorization cases plus strict HTTP format/no-write rejection and a live WEB2/3/4 golden-response **shape** suite. The latter exercises all six keyed WEB4 mutations (Sales and Goods Receipts Create/Update/Post), SQL rowversion conflict, read/list/context/status/lookup/balances/stock-card, and concurrent StockLedger/COGS/valuation against an independent nine-table SQL oracle. A 10-unit receipt at cost 10 followed by competing Sales posts with duplicate product/gift verifies final stock quantity **5**, inventory value **50**, and total COGS **50**.
8. After the six normal HTTPS cases, a separate **1/1 real two-client oversell** case concurrently posts two 4-unit Drafts against a 5-unit remaining balance. Require exactly one 200 and one 400 (`SalesReceipt.InsufficientStock`), one committed journal and ledger row, independent cost/balance checks, rejected Draft unchanged and original-key replay without duplication. It leaves one unit for fault injection. This test is explicitly CI-only and rejects staging/prod scope.
9. With Kestrel already admitted, a **separate CI maintenance identity** arms an ephemeral `AFTER INSERT` trigger on `dbo.StockLedger` for SalesReceipt rows only. Exactly **1/1** SQL fault case requires a sanitized HTTP 500, no Draft/header/cost/stock/valuation/ledger/journal writes, and no DDL for the runtime principal.
10. The maintenance identity removes the SQL trigger and confirms the original **exact schema13 fingerprint**. CI then **restarts production Kestrel**, checks verified HTTPS and SQL/security startup admission, and executes **1/1** recovery test on the original immutable operation key and rowversion. SQL journal/ledger/balance/COGS and same-key replay must prove no double-post. Cleanup still destroys the disposable database.
11. After verified rollback/restart recovery, the disposable bootstrap's two **additional distinct warehouses** exercise two simultaneous Sales.Post requests for the same ProductId on different WarehouseId keys. Independent SQL and HTTP oracles check receipt values `3 × 0.3333 = 0.9999` and `3 × 0.6667 = 2.0001`, precise duplicate-line cost splitting `0.1667 + 0.1666 = 0.3333`, the second sale COGS `1.3334`, two residual balances `2 / 0.6666` and `1 / 0.6667`, journal posting and zero change to the original warehouse. This adds **one 1/1 CI-only case**, not a staging/production certification.

12. The job demands exactly **five TRX files / 10 total executed and passed / zero skipped or failed**, uploads only sanitized TRX artifacts (not secrets, tokens, private keys or host logs), and destroys container and TLS material. The 178 frozen corpus files remain unchanged. A missing phase, TRX, DB cleanup, privilege or runtime verification is a CI **failure**, not an accepted exception.

### SQL Server 2022 metadata permission compatibility

Initial SQL13 preflight denied runtime under SQL2022 with `Security.WebRuntimePrincipalOverprivileged`. The independent diagnostic identified **`VIEW SECURITY DEFINITION`**, which (with `VIEW PERFORMANCE DEFINITION`) SQL2022 exposes as a narrower permission **implied by required `VIEW DEFINITION`**. The Web runtime elevated-permission query was revised to admit only these two implied metadata rights, retaining rejection of DML, schema privileges, admin roles, broad EXECUTE and grant option. No additional GRANT is issued. The original SQL2017/Windows graph and schema scripts 001–013 were not altered.
